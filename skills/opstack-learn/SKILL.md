# Capture a correction

## Foundation in the selected skills

[learn-taste](../learn-taste/SKILL.md), [skill-creator](../skill-creator/SKILL.md)

Base design-preference capture on learn-taste: trace rules to the user, preserve their reason, never invent preferences, and respect its approval requirements. Use skill-creator when the requested reusable result is a skill. An explicitly approved exact rule does not need approval again; inferred or expanded rules do. Read only the sources applicable to the current task and preserve their scope and requirements.


Start from the exact correction, the example that triggered it, and its stated reason. Separate a one-off task constraint from a durable preference. Keep project conventions in that project's established instruction or enforcement location; keep personal preferences at user scope. Do not infer a new global rule from one workaround or stylistic guess.

Choose the smallest effective home: an existing type/invariant, lint rule, test, project instruction, or personal instruction. Prefer executable enforcement for concrete defects when it materially helps. Read existing rules first, preserve unrelated guidance, and remove or narrow contradictions rather than stacking more rules.

When asked to save a preference, make the concrete change and verify its effect where feasible. If the user only asks for a retrospective, propose the rule without modifying settings. Show the saved rule, its scope, and evidence. Never mine unrelated private histories or change account configuration merely because this skill is active.
