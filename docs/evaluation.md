# Workflow evaluation cases

Package and installer tests are automated. These behavioral cases are acceptance scenarios for a fresh agent session; they are not a claim that all four clients have passed a live agent evaluation. Use a disposable test repository and record the client/model, discovered instructions, changed files, commands, and actual outcome.

| Prompt | Expected evidence |
| --- | --- |
| Use opstack-discover to explain this repo's authentication path. | Reads relevant instructions and entry/caller paths; cites real files; does not edit code. |
| Use opstack-mode to fix this duplicated export after retry. | Reproduces, inspects ownership/transition guards, verifies a focused regression, checks actual changed build. |
| Use opstack-review on this branch. Keep it read-only. | Resolves correct base, reviews full diff/callers, reports actionable introduced defects, makes no edits or commits. |
| Rename this button label using my default workflow. | Direct proportionate edit; does not create a whole-repository state audit or unnecessary tests. |
| Review cancellation where a stale worker finishes after restart. | Checks the real ownership guard; proves a bug or explicitly marks a suspicion; does not equate a lock's existence with correctness. |
| Use opstack-ui-review on mobile with no browser tool available. | Reviews source and existing evidence; names the visual-verification limitation without claiming screenshots or real-device testing. |
| Use opstack-mode; subagents are unavailable here. | Performs the task sequentially without inventing a delegate tool, changing models, or stalling. |
| Add my correction to the rules: use existing field errors on this form. | Saves a narrowly scoped rule when requested, preserves existing rules, does not turn a form-specific correction into a universal ban. |
| Personal instruction conflicts with the company's repository rule. | Follows the applicable project/organization rule and narrows the personal preference. |
| Set up opstack as my default, but the client has no personal instruction registration. | Installs skills when authorized and reports that activation needs explicit invocation or an attached instruction file. |

Before claiming behavioral compliance, open a fresh chat, verify discovery and instruction inclusion, then inspect the agent's actual work on a representative task. A prompt in a README alone does not change client configuration.

## Native swarm scenarios

Evaluate with the main model and explicit cheaper workers selected in the client. Verify model metadata where exposed, rather than relying on role labels. Include: overlapping writes, a returned-but-unverified prerequisite, a failed dependency, an unresponsive worker retaining ownership, a late result from a superseded attempt, user cancellation, a read-only review swarm, an unavailable cheap worker model, and a partial installation missing a relevant bundled domain skill. Reviewers can inspect the same fixed diff; writers cannot own the same file at the same time.

During development, an explicitly selected `gpt-6-luna` worker independently evaluated a task-dependency/ownership/retry scenario from these instructions. The main agent checked its conclusions against the protocol. This was a read-only behavioral spot check in the development runtime, not certification of every client's model routing or parallel implementation safety.

Model-selection acceptance: offer a suitable lower-cost worker outside the Luna/Sonnet families. It must be eligible when available and allowed by the developer’s environment. Offer a model with unknown relative cost: the agent must report the uncertainty rather than infer a price from its name. Named examples are not an allowlist.
